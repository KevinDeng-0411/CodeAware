# 记忆质量改进（MEMORY-1）— 当前边界与分层方案

> 本文档记录 CodeAware **长期记忆系统**的当前实现边界、缺陷清单与改进方案分档。
> 数据均为 2026-08-21 实测：长期记忆 52 行 / 知识 chunk 79 行 / 文档 58 / 会话 54。
> 原则：**评估后暂缓、条件满足再落地**（同 reranker / checkpoint / 实时高亮）。
> 面试叙事见 [面试深挖-简历逐条.md](../../interview/面试深挖-简历逐条.md) ④ 记忆。

---

## 1. 当前实现边界（实测）

| 维度 | 现状 | 证据 |
|---|---|---|
| 数据规模 | 长期记忆 52 行、知识 chunk 79 行 | 实测 `SELECT count(*)` |
| 向量索引 | `long_term_memories` / `knowledge_chunks` 均有 **HNSW** 索引（`vector_cosine_ops`） | `pg_indexes` 实测 |
| 抽取时机 | 会话达 4 条消息且无已抽记忆时**只抽一次**（`has_memories` 早退） | `memory_extract.py` |
| 事实封顶 | 单次最多 **5 条**原子事实 | `long_term.py` EXTRACT_PROMPT |
| 更新能力 | **无 `updated_at`、无 dedup、无冲突更新**（`save_prepared_facts` 盲插） | `long_term.py` |
| 删除通道 | **无软删除列、无 retention、无归档** | `long_term_memory` 模型（grep 无 `is_deleted/deleted_at`） |
| 时效 | 无 recency 加权、无召回时间窗 | `context_builder.recall_by_vector` |
| 召回阈值 | `mem_recall_threshold=0.5`（A 层已修，过滤噪声） | `config.py` + `context_builder` |

**关键判断（实测修正）**：因两表均有 **HNSW 索引**，向量库膨胀**不会导致检索速度线性下降**——
HNSW 是近似最近邻、亚线性检索。膨胀真正影响的是：**① 召回质量**（混入过期/无关事实 → 相似度漂移 + 噪声竞争 top-k）；**② 存储体积**。这决定了"D 层该如何做"（见 §4）。

## 2. 缺陷清单

- **F1 抽取只发生一次**：`has_memories` 早退使同一会话跨到再长也只抽首 5 条事实，早期信息不更新。
- **F2 无更新/去重/冲突**：同一事实（"用户用 FastAPI"）被重复插入 → 向量库冗余 + 检索 top-k 被相同事实挤占。
- **F3 无时效**：过期事实（用户换了技术栈）无 `updated_at` 支撑，无法按新旧加权或淘汰。
- **F4 无删除通道**：错误抽取/已撤回的事实无法清理，只进不退。

> 注：A 层（召回阈值 0.0→0.5）已在本次会话落地，F1-F4 仍存。

## 3. 改进方案分档（已实现 / 待实施）

### A 层（已落地 ✅）
- 召回阈值 0.5 过滤噪声（`mem_recall_threshold`）+ 提示词 v2"记忆仲裁"（记忆是线索非结论）。

### B 层（待实施）— watermark 增量抽取 + 冲突感知 save + 类型化
- **增量抽取**：用 `summary_message_count` 式 watermark，跨会话持续抽取（破 F1），替代"只抽一次"。
- **冲突感知 save**：写入前相似度匹配已有事实，`updated_at` 覆盖或合并（破 F2/F3 的一半）。
- **typed memory**：`memory_type` 语义枚举（FACT / REFERENCE / PREFERENCE），供召回分层与仲裁。

### C 层（待实施）— 时效加权 + 自然折旧
- **recency 加权**：召回按 `created_at` / `updated_at` 衰减相似度，近期事实优先（破 F3）。
- **自然折旧**：超时事实进入"低召回优先级"，而非物理删除。

### D 层（本轮讨论焦点，见 §4）
- 求"防膨胀 / 防召回质量劣化"的正确姿态，与"Celery Beat 定时清理"的取舍。

## 4. D 层：遗忘 / Retention 的正确做法（讨论结论）

**背景质疑**：是否"必须加 Celery Beat（定时，如每天一次）扫描软删除/过期，物理清理或冷归档"？
**结论**：**当前不该以"Beat 定时物理清理"方式落地；该以"检索层 recency 时间窗过滤"并入 C 层。** 理由（基于实测）：

1. **检索不会因膨胀线性退化**：HNSW 亚线性，实测记忆 52 行远未到检索瓶颈——"向量库无限膨胀→速度线性下降"对 HNSW 不成立；真正的劣化是**召回质量噪声**，不是速度。
2. **"防召回质量劣化"的正确工具是检索过滤，不是后台清理任务**：
   - `recall_by_vector` 加 `WHERE created_at > X`（时间窗）→ 即时生效、O(log)，过期事实自动出局。
   - 冷归档/物理删是"运维型任务"，为当前量级（几百行）引入 Celery Beat 每日扫描是**为了不可能的规模付费**。
3. **长期记忆是"事实"非"文档"**：文档要软删保审计，事实更适合"自然折旧 + 检索过滤"，不必 `deleted_at` + 归档管线。
4. **与 B/C 层合并**：一旦 B 层加 `updated_at`、C 层加 recency 加权，D 层的"过时不出现在结果"天然达成；无需单独清理任务。

**因此 D 层并入 C 层实现**，不单独立管线。触发条件（若未来达到才考虑物理清理）：
- 记忆行数 > 10 万 或 单查询向量扫描 > 数十 ms（HNSW 失效边界）；
- 或出现多用户/长会话膨胀（团队化阶段）。

**若真到清理那天**，优先"软删 + 按 `memory_type` 批量归档"而非"每日扫描"，且与 `run_tests_safe` 同款幂等守卫。

## 5. 面试要点（对口述加分）

> "我实测过记忆只有几十行，且向量表是 HNSW——所以膨胀不会让检索线性变慢，真的风险是召回质量混入过期事实。因此 D 层（遗忘/retention）我不做定时清理任务，而是把它并进 C 层的'时效加权 + 时间窗过滤'：`WHERE created_at > X` 让过时事实即时出局，O(log) 成本。等未来真到几万行、或团队化多用户时，再评估软删归档——在那之前，'物理清理任务'是过度工程。这个判断基于实测数据，不是我照抄行业模板。"
