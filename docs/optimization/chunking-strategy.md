# 分块策略：chunk_by_title 结构感知 + 长度兜底

> 状态：✅ 已实施（P3-3 起，C5 增强）
> 关联：ADR-0008（元素感知序列化）、[05 卡](../roadmap/current-release/05-文档解析与分块增强.md)
> 行为数据：2026-08-05 实测验证

## 1. 当前策略

**unstructured `chunk_by_title`**：按标题元素切分 + 长度上限 + overlap。

```python
# app/ai/rag/semantic_chunker.py
chunks = chunk_by_title(
    elements,
    max_characters=500,        # 单块上限
    new_after_n_chars=500,     # 积累超限后触发切分
    overlap=50,                # 相邻块重叠
    combine_text_under_n_chars=0,  # 不合并小节（每个标题独立成块）
)
```

## 2. 完整链路（str 契约）

```text
原始文档 (PDF / DOCX / HTML / MD)
  → ① 解析: unstructured partition() / pdfminer 字号检测
      → Elements: Title / ListItem / NarrativeText / Table
  → ② 序列化 (C5): Title→"# "、ListItem→"- "、其余原样
      → 纯文本（带结构标记）
  → ③ 重新解析: partition_md(text) → Elements
  → ④ 分块: chunk_by_title（标题边界 + 500字 + 50 overlap）
  → ⑤ 嵌入: bge-m3 → knowledge_chunks
```

**为什么不是"元素直通"**（解析出的 Elements 直接给 chunker）：
- `Document.content` 存储侧本质是文本，最终仍需序列化——元素直通收益被抵消
- 元素直通波及 `upload_document` 签名、全部 `SemanticChunker()` 构造点、monkeypatch 契约
- str 契约只改解析器输出，分块器一行未动（ADR-0008 决策）

**C5 之前的坑**：`str(e.text)` 压平元素丢类型 → DOCX/HTML/PDF 标题全失效 → 退化为 500 字定长滑窗。C5 改类型感知序列化后多格式标题生效。

## 3. 行为矩阵（实测 2026-08-05）

分块的驱动源是**标题元素**，不是文件扩展名：

| 文档内容 | 切分驱动 | 边界质量 |
|---|---|---|
| 有标题结构（`## 缓存击穿...`） | **标题边界优先** | ✅ 每块一个主题，语义完整 |
| 多段纯文本（无标题，累积>500字） | **段落边界切**（元素积累） | ✅ 每块是完整段落 |
| 短文本（<500字，无论有无标题） | 1 块不切 | ✅ 整段 |
| **单个超长段落**（一段>500字） | **字符硬切** | ⚠️ 唯一真正断裂场景 |

**关键实测**（669 字 3 段纯文本 → 2 块）：

```text
chunk[0]: 445 字 = 第一段 + 第二段（第二段完整结束）  ← 段落边界
chunk[1]: 222 字 = 第三段（完整）                     ← 段落边界
```

`chunk_by_title` 的元素积累逻辑：按元素（段落）累积，超 500 字后在**下一个元素边界**切；只有**单个元素本身**超 500 字才字符硬切。

## 4. 参数决策

| 参数 | 值 | 理由 |
|---|---|---|
| `max_characters` | 500 | 500 字 chunk × 5 条 ≈ 2500 字上下文，占 4K 窗口合理比例；太长稀释语义，太短碎片化 |
| `overlap` | 50 | 相邻块边界上下文不丢（跨块引用的实体/句子尾巴） |
| `combine_text_under_n_chars` | 0 | 不合并小标题下的小块——保持标题=主题的对应关系（匹配 Java 行为） |

### 4.0 参数可调化决定（2026-08-21）

**做了**：`chunk_size` / `overlap` 从硬编码升级为**可调配置** `rag_chunk_size=500` / `rag_chunk_overlap=50`（`.env` 可改，`SemanticChunker` 构造保留显式覆盖给测试/评估用）。**默认值不变 → 60 条 golden 基线 MRR 0.941 不受影响。**

**评估后暂缓 / 否决的动态化方案**：

| 方案 | 结论 | 理由 |
|---|---|---|
| 500 → 动态 500-600 + overlap 10% | ❌ 不做 | 500→600 对检索质量零可感影响，无触发问题 |
| **通用文档 800-1000 字 + overlap 10-15%** | ❌ **否决** | **撞 4K 窗口天花板**：800×top5=4000 字已近 `llm_max_tokens=4096`，叠加摘要/历史/用户问题必溢出。500 是被 4K 窗口推导的，不是拍脑袋 |
| 场景化全动态（按文档类型） | ⏸ 暂缓 | 三重复杂度（×场景×类型）、无触发（当前 58 文档以规整手册为主）；符合"无触发不引入"惯例。需要时用 `rag_chunk_size` 旋钮即可，不用改代码 |

**为什么可调配置 > 动态智能**：默认值守恒（不重测 golden）、未来要大块只需改 env、符合"评估后暂缓"惯例。

### 4.1 切分机制精确版：一个触发器 + 两种刀口

**关键：`500` 有两个角色，不能混为一谈。**

| 参数 | 角色 | 作用 |
|---|---|---|
| `new_after_n_chars=500` | **软上限**（`soft max`） | "块是否已满"的触发线——累积 ≥ 500 就不再塞下一个元素 |
| `max_characters=500` | **硬上限**（`hard max`） | 单个元素超过多长必须 **mid-text 劈开** |

**触发切分（时机）与落刀（位置）是正交的两件事**：

```text
触发：只看「当前块累积是否 ≥ 软上限 500」→ 满则触发切分
落刀：由边界类型决定
  ① Title 元素出现   → 无条件强切（哪怕块才 100 字）——标题是最高优先边界
  ② 达软上限后       → 在下一个元素（段落）边界切——保段落完整
  ③ 单元素 > 硬 500  → 字符硬切（mid-text）——唯一会切断句子的场景
```

**为什么"第 1 段 + 第 2 段同块 445 字"**：前两段未满 500（软上限未触发）→ 不切；加入第 3 段超 500 → 触发 → 在第 3 段边界落刀。**所以"未满 500 不切"是软上限的语义，不是段落本身主动触发切分。**

**参数固定但块长结构自适应**：`500 + 50` 是常量，但实际每块字数是"标题/段落边界 + 软上限"共同决定的**不等长**（实测 445/222，而非 500+169）。准确说法是"**固定参数 + 结构驱动的不等长切分**"——既不是定长滑窗，也不是动态智能。

## 5. 已知边界

- **单段超长文本**（一段 >500 字）字符硬切，可能切断句子——无标题无段落边界的极端场景
- 标题层级扁平化（`#`/`##`/`###` 都编成 `#`，层级信息丢失）
- 纯文本无主题边界（段落边界 ≠ 主题边界，一块内可能混多个主题）

## 6. 评估过的替代方案

| 方案 | 结论 | 理由 |
|---|---|---|
| 元素直通（list[Element] 给 chunker） | ❌ 不做 | 存储侧仍要序列化，收益抵消，改动面大（ADR-0008） |
| embedding 语义分块（chunk_by_similarity） | ⏸ 暂缓 | **定位 = "结构优先 + 语义兜底"的兜底**：结构分块已覆盖规整文档（手册/规范/教程，标题层级清晰）；语义分块补的是零散文本（会议记录/聊天/一句话经验，无标题可切 → 当前退化段落边界，单段超长的仍字符硬切）。每块一次 embedding + 聚类，个人项目规模无必要；触发条件：**知识库输入中"零散/无结构文本占比上升"**（当前 58 文档以规整手册/规范为主，未触发） |
| 单段超长 → 按句子切 | 📋 候选 | 解决唯一断裂场景；触发条件：纯文本占比高或单段超长常见 |
| 按元素类型分组（Table 独立块） | 📋 候选 | unstructured 原生支持；触发条件：知识库出现大量表格文档 |

## 7. 面试话术

> 「我的分块是结构感知的：chunk_by_title 按元素积累，有标题按标题切（每块一个主题），
> 没标题按段落边界切（多段纯文本实测在段落边界切分），只有单个段落超过 500 字才字符
> 硬切——这是唯一真正断裂的场景。C5 的关键是让 DOCX/PDF 的标题也能被这个策略看见：
> 解析器把元素类型编回 `#` 标记，分块器一行没改。我评估过 embedding 语义分块，但
> 当前知识库大多有结构，额外成本换不来可感知提升，所以保留结构优先 + 段落边界的策略。」
