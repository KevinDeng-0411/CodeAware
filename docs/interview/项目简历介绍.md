## 标准版（适合项目经历栏）

### 项目描述

**CodeAware** — 面向软件工程实验室团队（5-20 研发人员）的 AI 研发效能平台,核心功能涵盖 **RAG 智能问答知识库、ReAct Agent 自主检索、AI 代码评审、单测生成、AIReadMe 文档构建**；从 Java 全量重构为 Python 技术栈（FastAPI + LangGraph + PostgreSQL/pgvector/pg_search + Redis + Ollama bge-m3 + DeepSeek + React）,解决知识散落检索难、评审慢、新人上手慢三痛点,缩短研发提问到获取答案的链路。

### 项目亮点

**① 双模式智能问答（RAG + Agent）**：针对"单次检索问答无依据、复杂问题检索不到"的问题,设计 **RAG 确定性状态机（快省稳）与 ReAct 多步检索 Agent 双模式**,前端可切换。RAG 用 **BM25 + 向量 RRF 粗排 + ONNX reranker 精排** 混合检索带回引用来源；Agent 用 **LangGraph StateGraph**（agent/tools/reflect 节点）自主调度 5 个只读工具（知识/文档/计算/时间）,收敛感知停止；60 条 golden 检索基线 fused **MRR 0.941**,Agent eval **闭环率 1.0**、路由 60/60。

**② Agent 编排 + Reflection 自评**：针对 Agent 多步循环手写难维护、草稿输出不合格的问题,将循环编排为状态机图（防打转 / per-tool 上限 / 收敛检测）,并设计 **Reflection 自评**（draft 缓冲避免 token 泄漏、独立非 thinking 模型判定、不达标注入反馈重写）,**接受后一次性流式答案**,判定实时入 trace 供回放。

**③ 会话短期记忆**：设计并构建 **滑动窗口 + 增量摘要（水位线条件更新）+ Redis 缓存** 的短期记忆机制,PG 事务 commit 后才刷新缓存,保障多轮上下文完整、并发安全。

**④ 会话长期记忆**：设计并构建 **LLM 事实抽取 + pgvector 向量化存储 + 语义相似度召回（0.5 阈值过滤噪声）** 的长期记忆机制,跨会话召回用户偏好与团队事实;提示词内置"记忆仲裁"规则（记忆是线索非结论）,支撑个性化问答。

**⑤ RAG 召回优化**：通过 **查询重写（多查询扩展）+ 元素感知语义分块（按标题切,PDF 字号检测）+ 混合检索（BM25+向量 RRF）** 优化检索准确性——jieba 中文分词后 BM25 R@5 **0.25→1.000**,reranker 精排 MRR **+0.058**。

**⑥ LLMOps 观测闭环**：针对 Agent 黑盒、失败不沉淀的问题,落结构化 run trace（每步 token/耗时）+ 失败按 error/empty/工具异常分层评审,评审 accepted 后经 `sync_regression_cases.py` 一键沉淀进 eval 回归集（线上失败变门禁样本）;请求边界 guardrail fail-closed 注入检测。361 后端 + 62 前端测试全绿支撑。

### 技术栈

后端 FastAPI + SQLAlchemy 2 async + LangChain（ChatDeepSeek）+ **LangGraph**（检索路由 + Agent 编排）| 存储 PostgreSQL 16 / pgvector / pg_search（BM25）+ Redis 7 | Embedding / 检索 Ollama bge-m3 + ONNX reranker（bge-reranker-v2-m3）| 前端 React + Vite + TypeScript | **异步 Celery 任务（文档分块 / 记忆抽取）+ Kafka 事件流** | 10 表 / 41 API / 18 篇 ADR | 361 后端测试 + 62 前端测试 | Alembic 0014

### 工程素养（后端通用能力）

- **异步任务队列（Celery）**：上传文档分块 + 记忆抽取异步执行，任务**幂等（先查再写）+ 重试（max_retries=3）**，长外部调用不阻塞请求线程
- **缓存分层与一致性**：PG 为真相，Redis 缓存消息窗口/摘要/**答案（TTL 5min）**；`lru_cache` 复用模型单例；Redis miss 回查 PG 精确重建，不盲目 append
- **幂等与去重**：Kafka 按 `event_id` 幂等消费、任务重试前查幂等、guard 释放幂等
- **并发控制**：同会话并发 409 不进入模型、摘要水位线条件更新、Prompt 版本 PG advisory lock + savepoint 重试
- **事务边界**：短事务两段 commit，外部 LLM/embedding 等待期间不持有 DB 事务
- **安全边界**：请求层注入检测（fail-closed）、工具只读、admin/member 权限

## 深度版（面系统设计/架构岗）

### 项目概述

CodeAware 是为**软件工程实验室团队**设计的 AI 研发效能平台,从 Java（Spring Boot + LangChain4j 四模块）全量重构为 Python。针对实验室三个具体痛点：① 代码评审依赖人工、反馈慢；② 新人培训靠老成员口头传帮带,知识传递效率低；③ 团队文档（编码规范、架构设计、项目复盘）散落各处,没统一检索。提供 **Chat、Code Review、Unit Test、AIReadMe、Knowledge、Memory、Prompt** 七大功能,当前处于本地单用户阶段（团队化路线已规划：S1 项目隔离 → S2 分层重构 → S4 只读工具 Agent → S5 仓库感知）。以 **Chat 为核心域**,其余模块复用 Prompt 版本化 + 结构化输出 + 持久化基建。

### 架构决策与实现

**1. 自设计 typed SSE 协议（10 事件）**

裸 `data: token` + `[DONE]` 无法证明数据库提交成功,也区分不了"降级"和"失败"。设计 10 事件类型：`chat.started`（USER 已 commit,带真实 cid）→ `context.warning`（增强降级）→ `context.references`（检索来源,可溯源 RAG）→ `reasoning.delta`（模型思考过程流式）→ `token.delta`（生成内容）→ `tool.call` / `tool.result`（Agent 工具轨迹）→ `post_turn.warning`（后处理降级）→ `chat.completed`（ASSISTANT 已提交 + 全部收口）/ `chat.failed`。每个事件带 `protocol_version=1` + `sequence` 严格递增 + `turn_id`。同步接口 drain 同一事件流,状态机只有一份。

**2. PG-first 一致性模型**

`PG commit → Redis refresh`,而非常见的 Redis-first。USER/ASSISTANT 先写 PG 并 commit,再刷新 Redis 缓存（最近 20 条,TTL 7 天）。Redis miss → 回查 PG 并精确重建缓存,不盲目 append。增量摘要 `summary_message_count` 水位线 + PG 条件更新实现乐观并发控制,旧结果不覆盖新摘要。

**3. 短事务 + 外部调用分离**

LLM/embedding 等待期间不持有数据库事务：`短事务 PG 读写 → 关闭 session → 外部 LLM/embedding → 新短事务落结果 → commit`。RAG 查询先 `prepare_search`（查询改写 + embedding 预生成）再进入纯 SQL 的 `search_prepared`,一条 SQL 也不跨网络。

**4. 混合检索：BM25 + pgvector → RRF**

| 组件 | 实现 |
|---|---|
| 向量腿 | bge-m3 1024 维,HNSW cosine,`ORDER BY cosine_distance LIMIT top_k*3` |
| 词法腿 | ParadeDB pg_search 真 BM25（default tokenizer）,pg_trgm 为回退后端 |
| 融合 | RRF `1/(60+rank)`，结果标记 match_type（vector/keyword/both） |
| 多查询 | QueryRewriter 生成增强主查询 + 2-3 变体,去重后取 Top-K |

60 条 golden 基线（中文/英文/稀有标识符/语义改写/负例/跨文档）,RRF 融合 MRR **0.934**（C3 pg_trgm 仅 0.906,纯向量 0.920）,稀有标识符 MRR **1.000**;加 ONNX reranker 精排后 **MRR 0.941**（+0.058）。C4 BM25 升级后 fused 反超纯向量,实现 1+1>2。

**5. 元素感知文档分块 + PDF 字号标题检测**

解析器类型感知序列化（Title→`#`、ListItem→`-`）,分块器 `chunk_by_title` 一行没动,最小改动面让 DOCX/HTML/PDF 从定长滑窗恢复为按标题切。PDF 走 pdfminer 直接布局分析（字号众数=正文,>正文+0.5pt 且 ≤12 词=标题）,不走 `unstructured.partition.pdf`（避 torch/opencv/onnxruntime 视觉模型栈）。扫描版 PDF 通过 pypdf 文本层探针显式拒绝（`KNOWLEDGE_PDF_NO_TEXT_LAYER`）。

**6. Chat 引用与思考过程（C6）**

`context.references` 下发实际注入 prompt 的知识 chunk + 记忆,前端可折叠来源卡片（带 match_type 徽标）;`reasoning.delta` 流式展示模型原生思考,前端可折叠窗 + 答案开始后自动收起。关键坑：`ChatOpenAI` 不提取 `reasoning_content`（langchain 官方明示 third-party 字段丢弃）,切 `ChatDeepSeek` 后 spike 验证通过。

**7. 工程化与安全测试**

- 后端 361 tests，前端 62 tests，41 API，10 数据表，Alembic head 0014
- `run_tests_safe.py`：每次创建随机 disposable PG/Redis，拒绝 `ai_center`/`ai_center_py`/Redis DB 0,无论成功失败中断都精确清理
- 18 篇 ADR（0001-0018）记录所有架构决策
- Celery 异步任务（文档解析、记忆抽取）+ Kafka 事件流（audit/metrics）
- C1-C6 阶段 evidence manifest 可机器验证

**8. LLMOps 闭环（ADR-0017）——把 Agent 从"黑盒"变成"可观测、可评测、可改进"**

围绕三个痛点落地：**Agent 黑盒、失败不沉淀、无 guardrail**。

- **run trace 持久化 + 回放**：`agent_runs` 表（turn_id 全局唯一），`react_loop` 累积 trace（thought/tool_call/tool_result/answer 按序 + 工具 doc_ids + **每步 tokens/耗时**，`_aggregate_usage` 汇总 usage_metadata 得总 token + 成本落 `agent_runs.usage` 列）+ `context_snapshot`（本轮注入的短时记忆摘要+窗口边界、长时记忆 memory_refs）。turn_coordinator 成功/异常/取消三终端点 best-effort 落库（写失败不 fail turn）。回放端点归属 JOIN 校验。**trace 默认只存元数据**（思考全文靠 `AGENT_TRACE_INCLUDE_REASONING=true` 打开，避免 JSONB 膨胀与隐私）。
- **失败沉淀 → eval 回归集**：`needs_review` 分层（error/empty/工具真实异常），前端 Agent Runs 页评审 accepted（填 expected_tools + category）→ `sync_regression_cases.py` 自动追加进 eval 的 `REGRESSION_CASES`——线上失败 run 变成门禁样本，"可持续改进"不靠人肉。
- **请求边界 guardrail（fail-closed）**：注入检测放在 `ChatRequest` validator（422 拒绝），刻意不在工具结果层做（知识库是策展内容，结果层模式匹配会误报且伤模型理解）。
- **前端 Agent Runs 页**：列表/统计/详情回放；**流程视图 = 三层架构**（静态 SVG + 事件流 + STAGE 映射表 + CSS class 切换点亮），事件源无关（回放喂 trace，未来实时喂 SSE）；doc 节点跳知识库、查看对话跳完整上下文、记忆区跳 Memory 页。
- **Memory-Ops 两 counter**：recall（RAG/Agent 双路径）+ extraction（含 count=0）→ `metrics.memory` Kafka 事件。

**9. LangGraph Agent 编排 + Reflection（ADR-0018）——把 ReAct 从手写循环迁到节点图，并加自评闭环**

- **StateGraph 迁移**：主循环从手写 while 迁到 LangGraph StateGraph（`agent_graph.py`），agent/tools/reflect 三个节点 + 条件边（`_route_after_*`）表达工具循环；收敛检测、防打转、per-tool 上限语义逐一保真。`react_loop.py` 变薄壳——签名与 SSE 契约零改动，前端无感。动因：面试叙事（主流编排标准）+ 可维护性（读图 vs 读手写循环）+ ADR-0016 预留的"多工具复杂度上升 LangGraph 更优"条件满足。
- **Reflection 生产化（v1.4.0）**：agent 生成草稿后 reflect 节点自评，不达标注入 feedback 再生成（`max_reflections` 上限）。三个工程坑：① **draft token 泄漏**——反射拒绝时草稿 token 已流到前端，导致"草稿+重写"拼接 ≠ 落库 text；用**节点级缓冲**（`draft_deltas` 经节点 return 更新，非原地改 state）只在答案被接受后一次流出的修法；② 结构化输出对 thinking 模型走不通——Reflection 用**独立非 thinking 模型**（`get_chat_model(thinking=False)`）+ `with_structured_output(method="function_calling")`（DeepSeek 实测矩阵：json_schema 400、function_calling 仅非 thinking 可用）；③ 修了结构化输出 double-call bug（非 verdict 结果直接解析返回，不二次调用）。
- **trace 标记 Reflection**：reflect 步骤入 trace（attempt/accepted/feedback/ms），前端可看到"答案被拒→重写"过程。

### 已知边界（面试时主动说明）

- 当前为**本地单用户/单进程**,per-conversation guard 非跨进程 lease
- Agent 模式是**检索层决策形态**（只读 5 工具），不执行外部动作：sandbox/patch/shell/审批/Git 写入/MCP/多 Agent 仍锁（S1-lite→S5-lite 逐阶段授权）
- **Reflection agent 模式默认开**（`agent_reflection_enabled=true`，kill-switch 可关；RAG 无循环不受影响）；收敛强制终答的轮次**刻意绕过反射**；被拒草稿轮显示 reasoning 但答案 token 在接受后才一次出现（draft 缓冲的产品语义）
- RRF 粗排 + ONNX cross-encoder 精排（bge-reranker-v2-m3,MRR 0.941）
- 引用是"参考来源"（检索结果透明化）,不依赖 LLM 显式 cite
- 思考过程默认不持久化（`agent_runs.trace` 只存元数据；`AGENT_TRACE_INCLUDE_REASONING=true` 才存全文）
- Chat 页实时高亮（P2）**评估后暂缓**：FlowTrace 三层架构设计成**事件源无关**（SSE 推实时 + 轮询补全局），P2 只需把事件源从回放 trace 换成实时 SSE；但评估后判断回放页自动播放已覆盖"看到执行过程"的核心价值，实时时序复杂度（并行工具/收敛强制终答）与 ROI 不符，暂缓——架构留低成本切换路径（同 reranker/ReAct 的"评估后暂缓、条件满足再落地"模式）
- 扫描版 PDF 不支持 OCR
- PDF 表格压平为纯文本流（pdfplumber extract_tables 已评估、无表格文档暂缓）
