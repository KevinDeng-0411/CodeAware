## ① 双模式智能问答（RAG + Agent）

**简历这条想说**：不是单一模型调用，而是 RAG 确定性状态机 + Agent 自主检索两条路径，前端可切换，各自有实测。

**追问 1：为什么不做纯 Agent，而是双模式？**
- **一句应答**：ReAct 优势在多步推理/工具组合，劣势是对简单问题太重（延迟/成本/可靠性）。RAG 是确定性状态机、快省稳，覆盖 90% 单轮知识问题；Agent 只处理复杂多步场景。双模式 = 各司其职，RAG 默认。

**追问 2：RAG 和 Agent 后端怎么切换？」
- **一句应答**：`settings.chat_mode` + 前端按请求传 `mode` 覆盖。mode 进缓存 key 不互串；同一 Coordinator 内部按 mode 分支走 RAG（一次 astream）或 `react_loop`。

**追问 3：Agent 的 5 个工具职责？工具和检索是什么关系？**
- **一句应答**：search_knowledge / get_document / list_documents / calculate / get_current_time。search_knowledge **套壳完整 RagService**（QueryRewriter + RRF + reranker 一个字节不改），检索是"地基"，Agent 只在其上加决策层。

**追问 4：MRR 0.941 怎么测的？golden 集是什么？**
- **一句应答**：60 条 golden 检索基线（中文/英文/稀有标识符/语义改写/负例/跨文档），pipeline 跑混合检索得出 fused MRR（RRF 粗排 → reranker 精排）。稀有标识符 MRR 1.000。

**追问 5：收敛感知停止是什么？**
- **一句应答**：模型自评（prompt 引导"信息够不够"）+ 检索收敛检测（本轮 doc_ids ⊆ 已见 doc_ids → 打转 → 强制终答）+ per-tool 上限 + MAX_STEPS 4 硬兜底。eval avg_steps 2.28 → 2.17，闭环率保持 1.0。

## ② Agent 编排 + Reflection 自评

**简历这条想说**：Agent 不是"手写 while"，是 LangGraph StateGraph 组织节点/条件边 + Reflection 自评。

**追问 1：为什么把手写 ReAct 迁到 LangGraph？**
- **一句应答**：一开始手写 while（单工具、确定性状态机，显式 Python 更好证明事务边界）；Agent 落地后启发式变多（防打转/per-tool 上限/收敛检测），ADR-0014 预留的"多工具复杂度上升 LangGraph 更优"条件满足才迁。**是编排形态升级，不是多 Agent 平台化**——checkpoint/多 Agent 不引入。

**追问 2：LangGraph checkpoint 为什么不用？**
- **一句应答**：我的对话真相在 PG，每轮从 PG 重建 messages 喂给图——这本身就是我的持久化方案。Checkpointer 解决的状态续接问题在我的架构里不存在，反而带来双份持久化 + 状态序列化约束（图闭包捕获 model/tool_map，没法干净序列化）。

**追问 3：Reflection 怎么实现？draft 缓冲是什么？**
- **一句应答**：agent 节点产完 draft 后 reflect 节点用独立模型自评，不达标注入 feedback 再生成（max_reflections 上限）。**draft 缓冲**：反射轮 content delta 不立刻流，先进 buf，只有被接受的答案才一次流出——修的是"反射拒绝时草稿 token 已经流给前端"导致的草稿+重写拼接泄漏。

**追问 4：为什么 Reflection 用非 thinking 模型 + function_calling？**
- **一句应答**：DeepSeek 实测矩阵：json_schema 全 400、function_calling 仅非 thinking 可用、json_mode 都可用。thinking 下 function_calling 冲突，所以独立 `get_chat_model(thinking=False)` + `with_structured_output(method="function_calling")`。别忽略"我实测过兼容矩阵"这个加分点。

**追问 5：反射会不会永远不过 / 卡死？**
- **一句应答**：硬上限 `max_reflections`（默认 1）+ 收敛强制终答的轮次**刻意绕过反射**（stop_reason=converged 直接 END，不为反射而反射）。被拒草稿轮的 UX 语义是"显示 reasoning、答案在接受后一次出现"，可能看着像卡住——产品备注，非 bug。

**追问 6：节点怎么把事件送出来？（事件通道？）**
- **一句应答**：节点内 `get_stream_writer()` 发 custom 事件（reasoning/token/tool_call/tool_result），薄壳 `react_loop` 从 `graph.astream(stream_mode=["custom","values"])` 取，翻译成 typed SSE。**节点是 async 函数不能 yield**（中间 yield 会被 LangGraph 丢弃），所以走 writer。`draft_deltas` 必须走节点 return 覆盖（LastValue 通道），不能原地改 state。

## ③ 会话短期记忆

**简历这条想说**：多轮上下文靠滑动窗口 + 增量摘要，PG 真相 Redis 缓存。

**追问 1：为什么 PG 是真相、Redis 只是缓存？**
- **一句应答**：消息/摘要要外键、迁移、约束、审计，Redis 做不到。所以 **PG commit → Redis refresh**（不是 Redis-first），Redis 先写 + PG 回滚 = 幽灵数据。

**追问 2：增量摘要水位线是什么？防什么？**
- **一句应答**：`summary_message_count` 只推进**实际进了 Prompt 的消息数**；摘要按"旧摘要 + 最旧未摘要消息"增量合并，条件更新防并发旧结果覆盖新摘要。

**追问 3：Redis miss 怎么恢复？**
- **一句应答**：回查 PG 精确重建缓存，不盲目 append；重建失败发 context.warning，PG 继续当真相，回答不降级。

## ④ 会话长期记忆

**简历这条想说**：跨会话记忆 = LLM 抽取原子事实 + 向量召回 + 阈值滤噪 + 提示词仲裁。

**追问 1：短期 / 长期记忆的边界？**
- **一句应答**：短期 = 会话工作集（消息窗口 + 增量摘要，多轮连贯）；长期 = 跨会话原子事实（"用户用 FastAPI"，pgvector 召回）。来源/粒度/生命周期不同，不能混一张表。

**追问 2：召回阈值 0.5 是拍脑袋吗？**
- **一句应答**：不是。原来 0.0 全召回，随便一个问题都灌 5 条无关记忆进 prompt；改成 `mem_recall_threshold=0.5` 后实测：无关查询从 5 条噪声（sim≈0.46）→ 0 条。阈值可 env 调。
<br/>**别踩坑**：别空口说"提升效果"，把"0→5 条→0 条"的实测拿出来——这是 A 层修复的证据。

**追问 3：记忆和知识库冲突怎么办？**
- **一句应答**：提示词 v2 内置"记忆仲裁"：记忆是**线索不是结论**，与知识库冲突以知识库文档为准并说明差异。这是规则，不是代码强约束——靠 prompt 治理。

**追问 4：记忆有没有缺陷？诚实版。**
- **一句应答**：有。单会话达到 4 条消息且无已抽记忆时**只抽一次**（`has_memories` 早退）、5 条事实封顶、无 dedup/冲突更新/`updated_at`、无删除通道。改进按 **A/B/C/D 四层**在[记忆质量改进](../roadmap/current-release/08-记忆质量改进.md)里自洽推进：
  - **A 层（已落地）**：召回阈值 0.5 滤噪 + 提示词 v2 记忆仲裁；
  - **B 层**：watermark 增量抽取（破"只抽一次"）+ 冲突感知 save（破盲插）+ typed memory；
  - **C 层**：`created_at`/`updated_at` 时效**加权**（软排序——窗内事实按新近排序，近期优先）；
  - **D 层并入 C**：`WHERE created_at > X` **时间窗过滤**（硬门槛——超窗事实完全不进候选）。
<br/>**区分"时间窗 vs 时效加权"（面试易被追问）**：二者互补不是替代——时间窗管**过滤候选**（太旧没资格，剔除），时效加权管**排序候选**（窗内谁更相关，近期优先）。只留窗口则窗内新旧平权，过旧事实会挤占 top-k；只留加权则超窗噪音仍能召回。一起才完整。
- **别踩坑**：不说"我加了遗忘/清理"——当前**未落地**，且 D 层不以"Celery Beat 定时物理清理"实现（HNSW 亚线性、膨胀劣化的是召回质量非速度，正确姿态是 C 层时间窗，触发条件记录在案）。诚实讲"缺陷 + 分层 + 何时才做"。

**追问 5：长程任务怎么做？为什么要 checkpoint/note 而不是摘要压缩？**
- **一句应答**：长程任务要的不是"记住发生了什么"（摘要），是"现在在哪、做过什么、下一步干嘛"（状态）。我倾向**结构化 checkpoint**：窗口硬切分换新窗口 + 事件点用结构化输出把状态分成**已完成/进行中/下一步**写进外部 note，history 全量存档、需要时按需检索回填——比摘要更接近 agent 的最小充分上下文。
- **三个必防的坑**：① checkpoint 要用显式 schema（三分类）在明确事件点生成，不能靠模型自由发挥；② history 是"检索回填"不是"整段塞回"（否则等于没切窗口）；③ note 要带来源引用、可回查原文，否则"未完成"被写错就不可逆。
- **别踩坑**：这个方案我**当前没落地**——因为两个模式都没有"长程任务"这个触发条件（RAG 是问答、Agent 是单轮有界 MAX_STEPS=4，turn 结束即落库）。习惯是"评估后暂缓、条件满足再落地"（同 reranker/checkpoint）：**只在 Agent 方向预留，触发条件 = ① 出现用户跨多会话持续推进同一目标；② Agent 升级为持久目标代理**。条件没满足，它是未来预留不是当前债务。

## ⑤ RAG 召回优化

**简历这条想说**：检索不是单一向量，是多查询改写 + 混合召回 + RRF 粗排 + reranker 精排，每步有实测。

**追问 1：为什么 BM25 + 向量，不只向量？**
- **一句应答**：向量擅长同义（缓存击穿≈热点 Key 失效），BM25 擅长词面精确（类名/版本号/错误码）。互补，RRF 按排名融合（不依赖不可比原始分数）。C4 真 BM25 让 fused MRR 反超纯向量，1+1>2。

**追问 2：RRF 是什么？为什么不用加权？**
- **一句应答**：`1/(k+rank)`（k=60），按两腿排名融合，融合的是"位置"不是"分数"，因为向量 cosine 和 BM25 分数不可比。加权需要标定权重，RRF 无参数更稳。

**追问 3：reranker 为什么用 ONNX？原来为何暂缓？**
- **一句应答**：初评因 torch 依赖暂缓（MRR 0.934 已高 + 0.5s 延迟）；60 条 golden 暴露 cross_doc MRR=0.750 短板 + ONNX Runtime 无 torch 依赖后落地，MRR 0.883→0.941（+0.058），cross_doc 0.750→1.000。**"评估后暂缓、条件满足再落地"是叙事重点**。

**追问 4：jieba 分词解决了什么？**
- **一句应答**：default tokenizer 不拆中文，"缓存击穿如何解决"整个当一个 token 匹配不到；jieba 应用层分词后中文精确 R@5 0.25→1.000，BM25 R@5 0.600→0.943。**这个优化价值远超 reranker（MRR +0.28 vs 门禁 +0.01）**。

**追问 5：查询改写 / 多查询是什么？**
- **一句应答**：口语转正式技术表达 + 补缺失关键词 + 扩展过短问题，产出增强主查询 + 2-3 个变体，去重后取 Top-K。

**追问 6：reranker 具体怎么精排？是 (query, 文档) 成对推理吗？**
- **一句应答**：是，且是**拼接成一个序列**的双向交互（cross-encoder），不是独立编码。`[CLS] query [SEP] doc [SEP]` 一起进 Transformer，query 每个 token 能 attend 到 doc 每个 token（[reranker.py:73-88](file:///codeaware-py/app/ai/rag/reranker.py#L73-L88)）。bi-encoder（bge-m3，query/doc 各自独立编码再算余弦）速度快、doc 向量可预计算 → 负责全库粗召回 top20；cross-encoder（bge-reranker-v2-m3）准、但每对要现算不能缓存 → 只在 20 个候选上精排到 top5（[reranker.py:97-121](file:///codeaware-py/app/ai/rag/reranker.py#L97-L121)）。
- **实现细节**：`rerank(query, candidates, top_k)` 用**原始用户问题**（非改写 query）作 rerank_query → `for c in candidates` 逐对 `_encode_pair` + ONNX `_score` → `sorted(zip(scores,candidates), reverse=True)[:top_k]`，并把 chunk.score 替换成 cross-encoder logits（前端展示）。
- **链路全貌**：改写子 query 各跑 向量+关键词 混合召回 → RRF 融合去重成池（`reranker_top_n`=20）→ cross-encoder 精排 top5。

**追问 7：真实走查证据（rerank 动序 / 噪声剔除，面试最硬的弹药）**
- **一句应答**（真实 query "DeepSeek thinking 模式下怎么使用工具调用"，实测输出）：
  - **粗排池挤成一团**：RRF 分全在 `+0.022~+0.031`，拉不开差距（RRF 只看排名位置、不看实际相关）；且噪声混入——"缓存击穿 / 缓存穿透 / 缓存雪崩 / 微服务一致性"这些**与 query 无关**的 chunk 因沾边被 RRF 抬进池。
  - **精排把分拉开 + 动序 + 剔噪**：cross-encoder 分从 `+3.46`（强相关）到 `-4.52`（弱相关）区间拉开；`粗排#6 → 精排#4`、`粗排#18 → 精排#5`（LongTermMemory 文档被粗排埋没，reranker 捞回）；"缓存击穿"等假命中**全部被踢出 top5**。粗排前5 命中精排前5 = **3/5**（动了序）。
- **为什么这就解释了 MRR 0.883→0.941 / cross_doc 0.750→1.000**：RRF 管"多路都命中"，reranker 才看"真实相关"。挤在 0.02 区间的粗排分没法区分真假，-4.5~+3.5 的 xe 分才能。**这是机理不是玄学**。

## ⑥ LLMOps 观测闭环

**简历这条想说**：Agent 可观测、可评测、失败可沉淀、成本可追踪。

**追问 1：agent_runs 记录了什么？trace 默认存多少？**
- **一句应答**：turn_id 全局唯一，trace（thought/tool_call/tool_result/answer 按序 + 每步 tokens/耗时）+ context_snapshot（本轮注入的短时摘要/窗口/长期记忆）。**默认只存元数据**，思考全文需 `AGENT_TRACE_INCLUDE_REASONING=true`（防 JSONB 膨胀 + 隐私）。

**追问 2：失败怎么沉淀进回归集？"自动"吗？**
- **一句应答**：失败 run 标 needs_review（error/empty/工具真实异常）→ 前端评审 accepted（填 expected_tools + category）→ `sync_regression_cases.py` **手动跑一次**追加进 `REGRESSION_CASES` → eval 门禁自动拼接。
<br/>**别踩坑（诚实关键）**：⚠️ "自动"是过满的说法——**沉淀靠脚本（半自动），且当前回归集是空集**（BASE 18 个标准 case 在跑）。面试被问"沉淀过几条？"就答"infra 闭环、本地样本少、BASE 在跑"，别硬说沉淀了真实样本。

**追问 3：guardrail 为什么放请求边界、不放工具结果层？**
- **一句应答**：注入向量是用户查询覆盖系统指令，拦截在请求边界 fail-closed。工具结果层做模式匹配会误报（知识库是策展内容，SQL/XSS 教学文档满屏关键字）且破坏模型理解。真实注入是查寻，不是工具返回。

**追问 4：成本怎么观测？**
- **一句应答**：每步从 usage_metadata 归一化 input/output/reasoning tokens + 耗时，`_aggregate_usage` 汇总落 `agent_runs.usage`。Reflection 用独立轻量（非 thinking）模型，是控制成本的刻意选择。

## 工程素养（后端通用能力）

**简历这条想说**：有真实的后端功底，不只在调 AI。

**追问 1：为什么文档分块 / 记忆抽取走 Celery，不就地做？**
- **一句应答**：embedding + 分块是长外部调用，放请求线程会阻塞响应；移后台任务 + 重试（max_retries=3）+ 幂等（先查是否已分块再写，防重复 create）。和"模型调用不持事务"同一套可运维性叙事。

**追问 1.1：Celery 的 broker 选型是什么？是 Redis list 还是 stream？**
- **一句应答**：Celery + **Redis 当 broker**（复用现有缓存组件，不引入 RabbitMQ），默认走 **Redis list**（LPUSH/BRPOP）。list 是 Celery 的成熟默认实现——ack、重投、visibility 已建在 list 之上；stream 的消费者组 / 逐条 ack 对 Celery 是重复的（Celery 自己管）。要更可靠可切 stream 模式，但单机量级 list 够用。

**追问 1.2：为什么不用 Kafka 的重试 + 消息持久化？**
- **一句应答**：因为 **Kafka 的 at-least-once ≠ 任务执行保证**。at-least-once 只保"不丢传递"，代价是"可能重放"——而文档分块/记忆抽取**恰是重放会生产重复数据的操作**，所以"不重复"仍要靠应用层幂等（先查是否已分块）。既然不丢靠 ack、不重复靠幂等，两套方案这一点完全等价；Kafka 强的是**事件流吞吐/重放/广播**，对单机几百条/天的任务量大炮打蚊子，还要另起组件。
- **语义分工（关键）**：Celery = **任务**（要做什么，需重试/幂等/结果）；Kafka = **事件**（发生了什么，可观测/审计/metrics counter）。文档分块/记忆抽取走 Celery，audit/metrics 走 Kafka——按"任务 vs 事件"两个角色分开选型，不是追技术。

**追问 1.3：业务幂等怎么实现的？做到多深？**
- **一句应答**：分两个深度，诚实讲：**文档分块是真幂等**——用业务键（document_id）存在性检查吸收 at-least-once 的重放，重复派发只返回同一结果；**记忆抽取是半幂等**——用 `has_memories` 早退挡重入，但 `save_prepared_facts` 仍是**盲插**（无 dedup/conflict）。半幂等不是忘了，是**已记录缺口**：B 层改进要改成"冲突感知 save"。能讲清"哪层已幂等 / 哪层只是早退 / 哪里还欠账"，比一句"我做了幂等"可信。

**追问 2：答案缓存 TTL 5 分钟，不会不一致吗？**
- **一句应答**：答案缓存是**可丢弃加速层**，key 含 mode 不互串、TTL 兜底过期；一致性靠"PG 真相 + 缓存只加速不决策"原则兜住，不做强一致承诺。

**追问 3：同会话并发 409 怎么实现？跨进程有效吗？**
- **一句应答**：per-conversation guard（进程内 set）——**只保证单 worker 内**；跨 worker 的 PG advisory lock 是团队化阶段的已知边界（诚实别吹）。

**追问 4：模型等待时为什么不开事务？**
- **一句应答**：LLM 可能跑 30 秒，占着连接池 = 高并发下崩溃。短事务读/写 → 关 session → 调 LLM → 新短事务落结果，两个 commit 明确边界。
