## ① 双模式智能问答（RAG + Agent）

**简历这条想说**：不是单一模型调用，而是 RAG 确定性状态机 + Agent 自主检索两条路径，前端可切换，各自有实测。

**追问 1：为什么不做纯 Agent，而是双模式？**
- **一句应答**：ReAct 优势在多步推理/工具组合，劣势是对简单问题太重（延迟/成本/可靠性）。RAG 是确定性状态机、快省稳，覆盖 90% 单轮知识问题；Agent 只处理复杂多步场景。双模式 = 各司其职，RAG 默认。

**追问 2：RAG 和 Agent 后端怎么切换？」
- **一句应答**：`settings.chat_mode` + 前端按请求传 `mode` 覆盖。mode 进缓存 key 不互串；同一 Coordinator 内部按 mode 分支走 RAG（一次 astream）或 `react_loop`。

**追问 3：Agent 的 5 个工具职责？工具和检索是什么关系？**
- **一句应答**：search_knowledge / get_document / list_documents / calculate / get_current_time。search_knowledge **套壳完整 RagService**（QueryRewriter + RRF + reranker 一个字节不改），检索是"地基"，Agent 只在其上加决策层。

**追问 4：MRR 0.941 怎么测的？golden 集是什么？**
- **一句应答**：60 条 golden 检索基线（中文/英文/稀有标识符/语义改写/负例/跨文档），pipeline 跑混合检索得出 fused MRR（RRF 粗排 → reranker 精排）。稀有标识符 MRR 1.000。

**追问 5：收敛感知停止是什么？**
- **一句应答**：模型自评（prompt 引导"信息够不够"）+ 检索收敛检测（本轮 doc_ids ⊆ 已见 doc_ids → 打转 → 强制终答）+ per-tool 上限 + MAX_STEPS 4 硬兜底。eval avg_steps 2.28 → 2.17，闭环率保持 1.0。

## ② Agent 编排 + Reflection 自评

**简历这条想说**：Agent 不是"手写 while"，是 LangGraph StateGraph 组织节点/条件边 + Reflection 自评。

**追问 1：为什么把手写 ReAct 迁到 LangGraph？**
- **一句应答**：一开始手写 while（单工具、确定性状态机，显式 Python 更好证明事务边界）；Agent 落地后启发式变多（防打转/per-tool 上限/收敛检测），ADR-0014 预留的"多工具复杂度上升 LangGraph 更优"条件满足才迁。**是编排形态升级，不是多 Agent 平台化**——checkpoint/多 Agent 不引入。

**追问 2：LangGraph checkpoint 为什么不用？**
- **一句应答**：我的对话真相在 PG，每轮从 PG 重建 messages 喂给图——这本身就是我的持久化方案。Checkpointer 解决的状态续接问题在我的架构里不存在，反而带来双份持久化 + 状态序列化约束（图闭包捕获 model/tool_map，没法干净序列化）。

**追问 2.5：Graph 的 State 是怎么存的？存数据库吗？节点间怎么不断读取/更新？**
- **先答"有哪些 State"（AgentState 共 19 字段，按职责 4 组记，不背顺序）**：
  - **A 账本组**（共享引用就地累积，不随 return 替换）：`messages`（对话轨迹）、`trace`（LLMOps 观测）；
  - **B 防打转/收敛组**（本轮控制账本）：`seen_calls`（判重）、`tool_counts`（per-tool 上限）、`observed_docs`（历史累计 doc_ids）、`round_doc_ids`（本轮新 doc_ids）、`converged_pending`（收敛→强制终答轮标记）、`converged_this_round`（本轮是否收敛）；
  - **C 步数/终态组**（标量，走 return LastValue 覆盖）：`steps`、`stop_reason`、`text`（终答）、`tool_calls_total`、`error_tools`、`has_tool_calls`、`tool_calls`；
  - **D 反射组**（Reflection 用）：`question`（原始问题）、`reflections`（已反射次数）、`reflection_done`、`draft_deltas`（草稿缓冲）。
  - **讲清单要点**：可变引用类（A）vs 标量类（C）更新机制不同；本轮新增（round_doc_ids）vs 全局累计（observed_docs）对照支撑收敛判断；路由信号（converged_this_round/has_tool_calls/reflection_done）图内消费 vs 终态（text/stop_reason）被 ReactLoopState 带出落库。
- **再答"存数据库吗"（三层击穿）**：
  1. **执行期：State 不在数据库**——它是每次 `graph.astream(init,...)` 调用时在**内存**新建的一份 AgentState（[react_loop.py:73](file:///codeaware-py/app/ai/agent/react_loop.py#L73) `init`），图跑完即弃；
  2. **观测期：值得留的字段被主动带出落库**——`state` 里 trace/text/steps/stop_reason 经 `ReactLoopState` 引用带出 → `turn_coordinator._persist_agent_run` → **`agent_runs` 表**（这是"我落库"，不是 LangGraph 自己存）；
  3. **跨轮续接不靠 State 靠 PG**——init 里的 `messages` 每轮从 PG 重建、`trace` 是 `ReactLoopState` 共享引用，State 只承载"这一轮转的临时量"。所以 State 用完即弃、每轮 fresh 不丢事实。
- **节点间不断读取/更新 = 通道语义**（两类）：
  - **共享可变对象**（list/dict 引用共享）：`state["messages"].append(...)` 原地改，所有节点看同一对象（[agent_graph.py:223](file:///codeaware-py/app/ai/agent/agent_graph.py#L223)）——LangGraph 把 state 当不可变快照，但快照装的是**可变引用**，append 改引用指向的 list，所以"累积"照样 forward；
  - **标量 / 必须重写的字段**（LastValue 通道）：节点 `return {"steps": step}` 新值**替换**旧值——`steps`/`stop_reason` 走这。
- **最易绊人的反例 `draft_deltas`**：它**必须走节点 return 覆盖**（`update["draft_deltas"] = buf`，[agent_graph.py:252](file:///codeaware-py/app/ai/agent/agent_graph.py#L252)），不能原地 `state["draft_deltas"]=buf`——LastValue 只认 return 的 dict，**不认"你换了引用指向"**。这是通道语义最容易踩的坑，也是面试官最爱挖的一层。
- **面试别踩**：别说"State 存在数据库"（错）；也别笼统说"Node 自动同步 State"（错——是两类通道，list/dict 靠引用、标量靠 return）。

  > **记忆备注（6 问倒推法，别背字段背问题）**：State 是 agent 运行时要回答的六个问题，字段是答案——「**聊到哪 = messages**；**想干嘛 = tool_calls/has_tool_calls**；**别重复 = seen_calls/tool_counts**；**别打转 = round_doc_ids ⊆ observed_docs → converged_pending**；**怎么停 = steps/stop_reason/text**；**要不要修 = reflection 三件套 question/reflections/draft_deltas**」。把一次回合讲成一个小故事就自然串出字段，比背清单省力且面试是"有画面的回答"。

**追问 3：Reflection 怎么实现？draft 缓冲是什么？**
- **一句应答**：agent 节点产完 draft 后 reflect 节点用独立模型自评，不达标注入 feedback 再生成（max_reflections 上限）。**draft 缓冲**：反射轮 content delta 不立刻流，先进 buf，只有被接受的答案才一次流出——修的是"反射拒绝时草稿 token 已经流给前端"导致的草稿+重写拼接泄漏。

**追问 4：为什么 Reflection 用非 thinking 模型 + function_calling？**
- **一句应答**：DeepSeek 实测矩阵：json_schema 全 400、function_calling 仅非 thinking 可用、json_mode 都可用。thinking 下 function_calling 冲突，所以独立 `get_chat_model(thinking=False)` + `with_structured_output(method="function_calling")`。别忽略"我实测过兼容矩阵"这个加分点。

**追问 5：反射会不会永远不过 / 卡死？**
- **一句应答**：硬上限 `max_reflections`（默认 1）+ 收敛强制终答的轮次**刻意绕过反射**（stop_reason=converged 直接 END，不为反射而反射）。被拒草稿轮的 UX 语义是"显示 reasoning、答案在接受后一次出现"，可能看着像卡住——产品备注，非 bug。

**追问 6：节点怎么把事件送出来？（事件通道？）**
- **一句应答**：节点内 `get_stream_writer()` 发 custom 事件（reasoning/token/tool_call/tool_result），薄壳 `react_loop` 从 `graph.astream(stream_mode=["custom","values"])` 取，翻译成 typed SSE。**节点是 async 函数不能 yield**（中间 yield 会被 LangGraph 丢弃），所以走 writer。`draft_deltas` 必须走节点 return 覆盖（LastValue 通道），不能原地改 state。

**追问 7：完整讲讲 Agent 流程——ReAct 的 Thought / Action / Observation 在本项目分别是什么？**
- **一句应答**：一回合 = 三阶段循环（[agent_graph.py](file:///codeaware-py/app/ai/agent/agent_graph.py)）：
  - **Thought（想）= `agent_node`**：`model.astream(messages)` 聚合 → 提取 `reasoning_content`（thinking 思考，**实时推 `reasoning.delta` 给前端**）+ 看 `accumulated.tool_calls` 决定调什么（[L176-193](file:///codeaware-py/app/ai/agent/agent_graph.py#L176-L193)）；回注含 `reasoning_content` 的 AIMessage（**DeepSeek thinking 硬约束，不回注 400**，[L223-229](file:///codeaware-py/app/ai/agent/agent_graph.py#L223-L229)）；
  - **Action（做）= `tools_node`**：`for tc in tool_calls` 取 name/args/call_id → 执行工具 + 发 `tool.call` 事件 + 记 trace（[L276-281](file:///codeaware-py/app/ai/agent/agent_graph.py#L276-L281)）；Action 前有**三道闸**——防打转(seen_calls) / per-tool 上限 / 超限改注入"请直接回答"；
  - **Observation（看）= 结果回注**：result 截断 2000 → 发 `tool.result` + 记 trace（含 doc_ids/ms）→ `messages.append(ToolMessage(...))` 让模型下轮看到（[L313-325](file:///codeaware-py/app/ai/agent/agent_graph.py#L313-L325)）；**带出 doc_ids 做收敛检测**（`round ⊆ observed` → 打转 → 强制终答）。
  - **循环与终止**：Thought→Action→Observation→Thought...，止于「无 tool_calls(终答) / 收敛强制 / MAX_STEPS=4」，最后过 `reflect_node` 自评 → 接受则流答案。
- **一句话串**："Thought 聚合流提 reasoning + 决定 tool_calls；Action 执行工具(带防打转/上限闸)；Observation 截断结果回注(带 doc_ids 判收敛)。三阶段循环，止于无工具调用/收敛/超步数，再过 reflect 自评。"
- **加分点**：Thought 不只是"内部推理"——它**流式播给前端**（reasoning.delta）；Observation 不只是文本回注——它**带 doc_ids 签名**驱动收敛判断。这两点让"我能看见 agent 在想什么、也知道它何时该停"。

## ③ 会话短期记忆

**简历这条想说**：多轮上下文靠滑动窗口 + 增量摘要，PG 真相 Redis 缓存。

**追问 1：为什么 PG 是真相、Redis 只是缓存？**
- **一句应答**：消息/摘要要外键、迁移、约束、审计，Redis 做不到。所以 **PG commit → Redis refresh**（不是 Redis-first），Redis 先写 + PG 回滚 = 幽灵数据。

**追问 2：增量摘要水位线是什么？防什么？**
- **一句应答**：`summary_message_count` 只推进**实际进了 Prompt 的消息数**；摘要按"旧摘要 + 最旧未摘要消息"增量合并，条件更新防并发旧结果覆盖新摘要。

**追问 3：Redis miss 怎么恢复？**
- **一句应答**：回查 PG 精确重建缓存，不盲目 append；重建失败发 context.warning，PG 继续当真相，回答不降级。

## ④ 会话长期记忆

**简历这条想说**：跨会话记忆 = LLM 抽取原子事实 + 向量召回 + 阈值滤噪 + 提示词仲裁。

**追问 1：短期 / 长期记忆的边界？**
- **一句应答**：短期 = 会话工作集（消息窗口 + 增量摘要，多轮连贯）；长期 = 跨会话原子事实（"用户用 FastAPI"，pgvector 召回）。来源/粒度/生命周期不同，不能混一张表。

**追问 2：召回阈值 0.5 是拍脑袋吗？**
- **一句应答**：不是。原来 0.0 全召回，随便一个问题都灌 5 条无关记忆进 prompt；改成 `mem_recall_threshold=0.5` 后实测：无关查询从 5 条噪声（sim≈0.46）→ 0 条。阈值可 env 调。
<br/>**别踩坑**：别空口说"提升效果"，把"0→5 条→0 条"的实测拿出来——这是 A 层修复的证据。

**追问 3：记忆和知识库冲突怎么办？**
- **一句应答**：提示词 v2 内置"记忆仲裁"：记忆是**线索不是结论**，与知识库冲突以知识库文档为准并说明差异。这是规则，不是代码强约束——靠 prompt 治理。

**追问 4：记忆有没有缺陷？诚实版。**
- **一句应答**：有。单会话达到 4 条消息且无已抽记忆时**只抽一次**（`has_memories` 早退）、5 条事实封顶、无 dedup/冲突更新/`updated_at`、无删除通道。改进按 **A/B/C/D 四层**在[记忆质量改进](../roadmap/current-release/08-记忆质量改进.md)里自洽推进：
  - **A 层（已落地）**：召回阈值 0.5 滤噪 + 提示词 v2 记忆仲裁；
  - **B 层**：watermark 增量抽取（破"只抽一次"）+ 冲突感知 save（破盲插）+ typed memory；
  - **C 层**：`created_at`/`updated_at` 时效**加权**（软排序——窗内事实按新近排序，近期优先）；
  - **D 层并入 C**：`WHERE created_at > X` **时间窗过滤**（硬门槛——超窗事实完全不进候选）。
<br/>**区分"时间窗 vs 时效加权"（面试易被追问）**：二者互补不是替代——时间窗管**过滤候选**（太旧没资格，剔除），时效加权管**排序候选**（窗内谁更相关，近期优先）。只留窗口则窗内新旧平权，过旧事实会挤占 top-k；只留加权则超窗噪音仍能召回。一起才完整。
- **别踩坑**：不说"我加了遗忘/清理"——当前**未落地**，且 D 层不以"Celery Beat 定时物理清理"实现（HNSW 亚线性、膨胀劣化的是召回质量非速度，正确姿态是 C 层时间窗，触发条件记录在案）。诚实讲"缺陷 + 分层 + 何时才做"。

**追问 5：长程任务怎么做？为什么要 checkpoint/note 而不是摘要压缩？**
- **一句应答**：长程任务要的不是"记住发生了什么"（摘要），是"现在在哪、做过什么、下一步干嘛"（状态）。我倾向**结构化 checkpoint**：窗口硬切分换新窗口 + 事件点用结构化输出把状态分成**已完成/进行中/下一步**写进外部 note，history 全量存档、需要时按需检索回填——比摘要更接近 agent 的最小充分上下文。
- **三个必防的坑**：① checkpoint 要用显式 schema（三分类）在明确事件点生成，不能靠模型自由发挥；② history 是"检索回填"不是"整段塞回"（否则等于没切窗口）；③ note 要带来源引用、可回查原文，否则"未完成"被写错就不可逆。
- **别踩坑**：这个方案我**当前没落地**——因为两个模式都没有"长程任务"这个触发条件（RAG 是问答、Agent 是单轮有界 MAX_STEPS=4，turn 结束即落库）。习惯是"评估后暂缓、条件满足再落地"（同 reranker/checkpoint）：**只在 Agent 方向预留，触发条件 = ① 出现用户跨多会话持续推进同一目标；② Agent 升级为持久目标代理**。条件没满足，它是未来预留不是当前债务。

## ⑤ RAG 召回优化

**简历这条想说**：检索不是单一向量，是多查询改写 + 混合召回 + RRF 粗排 + reranker 精排，每步有实测。

**追问 1：为什么 BM25 + 向量，不只向量？**
- **一句应答**：向量擅长同义（缓存击穿≈热点 Key 失效），BM25 擅长词面精确（类名/版本号/错误码）。互补，RRF 按排名融合（不依赖不可比原始分数）。C4 真 BM25 让 fused MRR 反超纯向量，1+1>2。

**追问 2：RRF 是什么？为什么不用加权？**
- **一句应答**：`1/(k+rank)`（k=60），按两腿排名融合，融合的是"位置"不是"分数"，因为向量 cosine 和 BM25 分数不可比。加权需要标定权重，RRF 无参数更稳。

**追问 3：reranker 为什么用 ONNX？原来为何暂缓？**
- **一句应答**：初评因 torch 依赖暂缓（MRR 0.934 已高 + 0.5s 延迟）；60 条 golden 暴露 cross_doc MRR=0.750 短板 + ONNX Runtime 无 torch 依赖后落地，MRR 0.883→0.941（+0.058），cross_doc 0.750→1.000。**"评估后暂缓、条件满足再落地"是叙事重点**。

**追问 4：jieba 分词解决了什么？**
- **一句应答**：default tokenizer 不拆中文，"缓存击穿如何解决"整个当一个 token 匹配不到；jieba 应用层分词后中文精确 R@5 0.25→1.000，BM25 R@5 0.600→0.943。**这个优化价值远超 reranker（MRR +0.28 vs 门禁 +0.01）**。

**追问 5：查询改写 / 多查询是什么？**
- **一句应答**：口语转正式技术表达 + 补缺失关键词 + 扩展过短问题，产出增强主查询 + 2-3 个变体，去重后取 Top-K。

**追问 6：RAG 粗排后为什么必须接入 cross-encoder 重排？**
- **一句应答**：因为**粗排（多路召回 + RRF）区分不了"真相关 vs 假命中"**——RRF 只管"多路都命中→排名高"，不管"命中的到底相不相关"。三条证据（真实走查，见 [rerank-pipeline.md](../optimization/rerank-pipeline.md)）：
  - **RRF 分物理拉不开**：池内全在 `+0.022~+0.031`（`Σ 1/(60+rank)` 只差千分之几），纯 sort 无判别力；
  - **噪声被"沾边"抬进池**：缓存击穿/穿透/雪崩、微服务一致性等**无关 chunk** 因沾了某改写变体的词就进 top20；
  - **cross-encoder 真正区分**：成对打分从 `+3.46` 到 `-4.52`（横跨 8 个数量级），动序（6→4、18→5）+ 真相关从 #18 捞回 + 噪声全踢出。
- **一句话机理**：RRF 解决"哪些文档多条腿都提到"（召回面/粗），cross-encoder 解决"哪些文档真的答得上"（排序精度/准）。粗排便宜够用于大集合，精排必须换"看真实相关"的模型。这就是 MRR 0.883→0.941 / cross_doc 0.750→1.000 的机理。
- **实现**：cross-encoder = `[CLS] query [SEP] doc [SEP]` 拼接双向交互（[reranker.py:73-88](file:///codeaware-py/app/ai/rag/reranker.py#L73-L88)）；bi-encoder（bge-m3，独立编码可预计算）管全库粗召回、cross-encoder（每对现算不可缓存）只管池内精排。

**追问 7：重排候选池数量如何界定？为什么是 20，依据是什么？**
- **一句应答**：候选池数量是**"效果 × 性能"平衡**的产物，不是越大越好：
  - **下界 = 不能漏优质文档**：reranker 只从池里选，池太小真相关根本进不来。实测就有真相关文档在粗排第 18、被 reranker 捞回 top5——池至少要宽到容得下"被粗排埋没但真相关"的候选。演进史 `rerank_pool=15 → top_k*4(=20)` 也是为留足这个空间。
  - **上界 = 延迟必须可控**：cross-encoder 是**逐对 ONNX 推理、不可预缓存**，池从 20→100 精排耗时线性涨、直接拉高接口延迟、恶化用户体验。这是 bi-encoder 便宜管粗召回、cross-encoder 贵管精排的分工边界决定的。
  - 所以 **top20 粗排足够宽、能容下绝大多数优质候选**，**top5 精排把精度保住、延迟控制在几十~几百 ms**——这是设计上给"多请求同时打接口"预留的平衡点。
  - **诚实边界**：20 不是 golden 扫描出的精确最优点，是平衡经验值 + 可调配置（`reranker_top_n`，注释明写"可调 20-30"）；当前单机未到高并发压力，但架构按这个平衡点设计，配置暴露可调。
- **链路上 fallback**：reranker 关时 `pool_k = top_k*2`；开时 `reranker_top_n`（20），去重后喂 reranker 精排 top5。

**追问 8：聊一聊分块策略——chunk 大小 / 重叠怎么配、如何选语义分块和结构分块、依据是什么？**
- **一句话立论**：当前是**结构分块**（`unstructured.chunk_by_title` 按标题切），**不是语义分块**——没有任何 embedding 参与。"元素感知"指解析层保类型（Title→`#`、ListItem→`-`）让 chunker 认出标题，不是语义。我的选型链条 = **机制（结构优先）→ 参数（可调配置，4K 窗口推导）→ 边界（语义兜底何时才值）**。
- **① 机制：一个触发器 + 两种刀口**（"500"有两个角色）：
  - 触发切分只看**软上限 `new_after_n_chars=500`**——块累积 ≥500 才"满"，不满继续塞下一个元素；
  - 落刀由边界决定：新 `Title` → **无条件强切**（哪怕块才 100 字，最高优先）；达软上限后 → 在**下一个段落边界**切（保段落完整）；只有**单个元素 > 硬上限 `max_characters=500`** 才 mid-text 字符硬切（唯一切断句子的场景）。
  - 所以块长**结构自适应且不等长**（实测切出 445/222 而非 500+169）——准确说法是"**固定参数 + 结构驱动的不等长切分**"，既不是定长滑窗、也别吹"动态智能"。
- **② chunk 大小 / 重叠怎么配**：暴露为**可调配置** `rag_chunk_size=500` / `rag_chunk_overlap=50`（`.env` 可改，`SemanticChunker` 保留显式传参给测试/评估）。**500 不是拍脑袋，是被 `llm_max_tokens=4096` 推导的**：500 × top5 ≈ 2500 字占 4K 窗口合理比例，太长稀释语义、太短碎片化。
  - **为什么不做更动态/更大的配置**：
    - 500→500-600 动态 → 对质量零可感，无触发问题；
    - **800-1000 通用默认 → 否决**：800 × top5 ≈ 4000 字已近 4096，叠加摘要/历史/用户问题/系统提示词 **必溢出**——业界常见值在这套架构里落地即炸；
    - 场景化全动态（按文档类型）→ **暂缓**：三重复杂度（×场景×类型）× 无触发（当前 58 文档以规整手册为主），符合"无触发不引入"惯例。
  - **为什么"可调配置" > "动态智能"**：默认值不变 → golden 基线 MRR 0.941 不重测；未来要大块只需改 env 不用改代码；是给未来的旋钮不是当前的复杂度。
- **③ 语义分块 vs 结构分块怎么选**：**结构优先 + 语义兜底**是方向，但分两层落：
  - **结构分块**（当前）：适合**规整文档**（手册/规范/教程，标题层级清晰）——按标题切保留完整语义单元和业务逻辑，不割裂上下文；
  - **语义分块**（暂缓）：适合**零散文本**（会议记录/聊天/一句话经验，无标题可切、段落边界≠主题边界）——靠 embedding 相似度聚合同主题，避免单一语义被切裂。
  - **当前未落地语义兜底的原因**：触发条件 = "知识库输入中零散/无结构文本占比上升"或"大量单段超长"，当前实测 58 文档以规整手册/规范为主，未触发。候选形状（纯文本按句子切、Table 独立块、语义聚簇分块）已记在 [chunking-strategy.md](../optimization/chunking-strategy.md)。
- **④ 选型依据总结**：三件事——**机制**选结构优先（解析层已结构化、能保标题=主题）；**参数**由 4K 窗口上限决定（500 是推导不是偏好）；**语义兜底**按"无触发不引入 + 评估后暂缓"（同 adr/记忆/reranker 一贯判断逻辑）。
- **别踩坑**：别自称"做了语义分块"（当前是结构分块）；别答"固定 500 字符"（那是定长滑窗、暴露理解浅）；也别吹"800-1000 更优"（没算 4K 窗口，会露馅——面试官可能自己算出来）。

## ⑥ LLMOps 观测闭环

**简历这条想说**：Agent 可观测、可评测、失败可沉淀、成本可追踪。

**追问 1：agent_runs 记录了什么？trace 默认存多少？**
- **一句应答**：turn_id 全局唯一，trace（thought/tool_call/tool_result/answer 按序 + 每步 tokens/耗时）+ context_snapshot（本轮注入的短时摘要/窗口/长期记忆）。**默认只存元数据**，思考全文需 `AGENT_TRACE_INCLUDE_REASONING=true`（防 JSONB 膨胀 + 隐私）。

**追问 2：失败怎么沉淀进回归集？"自动"吗？**
- **一句应答**：失败 run 标 needs_review（error/empty/工具真实异常）→ 前端评审 accepted（填 expected_tools + category）→ `sync_regression_cases.py` **手动跑一次**追加进 `REGRESSION_CASES` → eval 门禁自动拼接。
<br/>**别踩坑（诚实关键）**：⚠️ "自动"是过满的说法——**沉淀靠脚本（半自动），且当前回归集是空集**（BASE 18 个标准 case 在跑）。面试被问"沉淀过几条？"就答"infra 闭环、本地样本少、BASE 在跑"，别硬说沉淀了真实样本。

**追问 3：guardrail 为什么放请求边界、不放工具结果层？**
- **一句应答**：注入向量是用户查询覆盖系统指令，拦截在请求边界 fail-closed。工具结果层做模式匹配会误报（知识库是策展内容，SQL/XSS 教学文档满屏关键字）且破坏模型理解。真实注入是查寻，不是工具返回。

**追问 4：成本怎么观测？**
- **一句应答**：每步从 usage_metadata 归一化 input/output/reasoning tokens + 耗时，`_aggregate_usage` 汇总落 `agent_runs.usage`。Reflection 用独立轻量（非 thinking）模型，是控制成本的刻意选择。

## 工程素养（后端通用能力）

**简历这条想说**：有真实的后端功底，不只在调 AI。

**追问 1：为什么文档分块 / 记忆抽取走 Celery，不就地做？**
- **一句应答**：embedding + 分块是长外部调用，放请求线程会阻塞响应；移后台任务 + 重试（max_retries=3）+ 幂等（先查是否已分块再写，防重复 create）。和"模型调用不持事务"同一套可运维性叙事。

**追问 1.1：Celery 的 broker 选型是什么？是 Redis list 还是 stream？**
- **一句应答**：Celery + **Redis 当 broker**（复用现有缓存组件，不引入 RabbitMQ），默认走 **Redis list**（LPUSH/BRPOP）。list 是 Celery 的成熟默认实现——ack、重投、visibility 已建在 list 之上；stream 的消费者组 / 逐条 ack 对 Celery 是重复的（Celery 自己管）。要更可靠可切 stream 模式，但单机量级 list 够用。

**追问 1.2：为什么不用 Kafka 的重试 + 消息持久化？**
- **一句应答**：因为 **Kafka 的 at-least-once ≠ 任务执行保证**。at-least-once 只保"不丢传递"，代价是"可能重放"——而文档分块/记忆抽取**恰是重放会生产重复数据的操作**，所以"不重复"仍要靠应用层幂等（先查是否已分块）。既然不丢靠 ack、不重复靠幂等，两套方案这一点完全等价；Kafka 强的是**事件流吞吐/重放/广播**，对单机几百条/天的任务量大炮打蚊子，还要另起组件。
- **语义分工（关键）**：Celery = **任务**（要做什么，需重试/幂等/结果）；Kafka = **事件**（发生了什么，可观测/审计/metrics counter）。文档分块/记忆抽取走 Celery，audit/metrics 走 Kafka——按"任务 vs 事件"两个角色分开选型，不是追技术。

**追问 1.3：业务幂等怎么实现的？做到多深？**
- **一句应答**：分两个深度，诚实讲：**文档分块是真幂等**——用业务键（document_id）存在性检查吸收 at-least-once 的重放，重复派发只返回同一结果；**记忆抽取是半幂等**——用 `has_memories` 早退挡重入，但 `save_prepared_facts` 仍是**盲插**（无 dedup/conflict）。半幂等不是忘了，是**已记录缺口**：B 层改进要改成"冲突感知 save"。能讲清"哪层已幂等 / 哪层只是早退 / 哪里还欠账"，比一句"我做了幂等"可信。

**追问 2：答案缓存 TTL 5 分钟，不会不一致吗？**
- **一句应答**：答案缓存是**可丢弃加速层**，key 含 mode 不互串、TTL 兜底过期；一致性靠"PG 真相 + 缓存只加速不决策"原则兜住，不做强一致承诺。

**追问 3：同会话并发 409 怎么实现？跨进程有效吗？**
- **一句应答**：per-conversation guard（进程内 set）——**只保证单 worker 内**；跨 worker 的 PG advisory lock 是团队化阶段的已知边界（诚实别吹）。

**追问 4：模型等待时为什么不开事务？**
- **一句应答**：LLM 可能跑 30 秒，占着连接池 = 高并发下崩溃。短事务读/写 → 关 session → 调 LLM → 新短事务落结果，两个 commit 明确边界。

## 通用八股 · LLM 工程（不绑定单条简历）

> 这一栏放"概念性问题"——不属于某条简历亮点，但被问到要答得干净。

**Q：什么是结构化输出（Structured Output）？**
- **一句应答**：让 LLM 输出的不是自由文本，而是**符合预定义 schema 的结构化数据**（JSON/对象），程序可直接消费、无需脆弱的字符串解析。它把"模型当文本生成器"变成"模型当**类型化数据生产者**"。

**Q：实现结构化输出的方式有哪些？**
- **从原始到规范**：
  1. **Prompt + 手写解析**：提示"输出 JSON" + `json.loads`（最脆，格式漂移/带 markdown 就崩）；
  2. **JSON mode**：`response_format={"type":"json_object"}`，保证是合法 JSON，但不保 schema；
  3. **Function / tool calling**：把 schema 作为"函数签名"交给模型，模型**调用该函数**返回结构化参数——schema 由签名强制；
  4. **JSON Schema / Structured Outputs**：provider 原生严格模式（如 OpenAI strict schema），schema 强约束；
  5. **LangChain `with_structured_output(schema, method=...)`**：统一封装以上——`method` 选 `json_mode` / `function_calling` / `json_schema`。
- **项目落地**：`with_structured_output` —— 记忆抽取 `ExtractedFacts`(json_mode)、反射 `ReflectionVerdict`(function_calling)、代码评审 `CodeReviewResult`、检索路由 `_RouteResult`(json_mode)。**method 按 DeepSeek 实测兼容矩阵选**（json_schema 全 400；function_calling 仅非 thinking 可用；json_mode 都可用）。

**Q：结构化输出和 Function Calling 是什么关系？**
- **一句应答**：**Function calling 是结构化输出的一种实现机制**——工具调用的本质就是"模型输出一段符合函数入参 schema 的 JSON"。
  - **涵盖关系**：结构化输出 ⊃ function calling。function calling 的"参数"就是一次结构化输出，只是动机不同——工具调用的目的是**触发外部动作**，结构化输出的目的是**拿到数据**；
  - **反向借用**：拿一个目标 schema **伪装成"必须调用的函数"**，就能用 function calling 机制实现结构化输出——项目反射的 `method="function_calling"` 正是这么干的；
  - **同源**：两者底层都是 Pydantic → JSON Schema → 交给模型约束产出。

**Q：Pydantic 和 dataclass 差别？结构化输出为什么用 Pydantic？**
- **一句应答**：`dataclass` 是**纯数据容器**（不校验、不转换、不序列化，类型注解只是标注）；`Pydantic` 是**带契约的容器**（运行时校验 + 类型转换 + `model_dump`/`model_json_schema` 序列化 + ORM 投影）。
  - **结构化输出必须 Pydantic**：要 `model_json_schema()` 生成喂给模型的 schema、要校验"模型不可信输出"（`ExtractedFacts(facts="oops")` 会抛 `ValidationError`，dataclass 静默放过埋雷）、要序列化落库；
  - **内部可信数据用 dataclass**：项目的工具返回值 `ToolObservation` 是 `@dataclass`——只在同进程被解构消费、不给模型、不落库，Pydantic 能力用不上（白付校验开销）。

**Q：什么叫"跨边界"？（什么时候才该用 Pydantic）**
- **一句应答**："边界"= 数据**离开当前可信代码**、需要防御或传输的地方。四类：① **信任边界**（LLM 输出/用户输入不可信 → 必须校验）；② **序列化边界**（要 dump 成 JSON/入库）；③ **进程边界**（跨 HTTP）；④ **版本边界**（跨前后端契约，如 Typed SSE）。
- **选型判据**：**"这段数据会不会由不可信来源产生、或要序列化传出去？"** 会 → Pydantic（防在边界）；不会（内部流转）→ dataclass（省开销）。项目里 Pydantic 全部用在跨边界处：结构化输出 / tool schema / API 请求响应 / `BaseSettings` / SSE 事件。

**Q：Workflow 和 Agent 的区别是什么？本项目怎么选的？**
- **一句应答**：**区别只有一条——控制流由谁决定**。Workflow = **开发者/代码**决定下一步（确定性 DAG/状态机，快稳可预测但死板）；Agent = **模型**决定下一步（动态 tool choice loop，灵活但慢贵不可预测易打转）。
- **项目选型（双模式按任务形态分）**：
  - **RAG 模式 = Workflow**（确定性状态机：改写→检索→渲染→生成写死），覆盖 **90% 单轮知识问题**——不需要模型自主决策，workflow 更快稳省；
  - **Agent 模式 = Agent**（ReAct tool loop，模型自主选工具/决定何时停），留给 **10% 复杂多步**。
- **最该说的一层**：**agent 模式内部也是"workflow 骨架 + agent 决策"**——StateGraph 把 ReAct 循环骨架（条件边/防打转/步数上限）用代码定死，但每步调什么工具、何时收场由模型定。**"Agent 不是没有 workflow，而是把决策权交给模型、结构边界仍由 workflow 保证。"**

**Q：Agent 有哪些范式？你项目用的是哪个？**
- **一句应答**：主流范式 = **ReAct**（think→act→observe 交替，简单通用易解释，但无全局视野易打转）、**Plan-and-Execute**（先规划再执行，有全局视野但规划错则全错）、**Reflexion**（ReAct + 失败反思重试，纠错强但多一轮成本）、**ReWOO**（先规划工具调用再并行执行，省 token 但不能动态调整）、**Multi-Agent**（多角色协作，分工强但通信/调试难）。
- **项目归属**：**纯 ReAct + 轻量 Reflexion**——`agent_node`↔`tools_node` 是 ReAct，`reflect_node` 是 Reflexion 形态（自评拒绝→重写，但无跨轮反思库，比完整 Reflexion 轻）。**单 agent，无 plan-execute / multi-agent**（按"无触发不引入"暂缓，同记忆 D 层/多 Agent 逻辑）。

**Q：Skill 和 MCP 有什么区别？**
- **一句应答**：**MCP = 协议/接口标准（怎么连）**，**Skill = 能力包（会什么/怎么做）**。
  - **MCP**（Model Context Protocol）：开放协议，标准化 agent 如何连接外部工具/数据源（C/S：server 暴露 tools/resources，client 连）——解决**互操作/接入标准化**，像 USB-C，偏"运行时连接"；
  - **Skill**（Claude Agent Skills）：可复用能力包（SKILL.md 指令 + 脚本 + 资源），**按需加载**——解决**领域知识/流程的封装 + 渐进式披露**（不占常驻上下文）；
  - **关系**：可组合——一个 Skill 可指导 agent 去调用某个 MCP server。
- **项目对照**：CodeAware **没用 MCP**（工具自研 `@tool`）；waku-agent 有 `tools/mcp_client.py`——两项目正好"自研工具 vs 接 MCP"可对比。

**Q：上下文压缩策略有哪些？项目用了哪些？**
- **一句应答**：策略谱系——① 滑动窗口（丢最旧）；② 增量摘要（老消息摘要合并）；③ 分层/递归摘要（摘要的摘要）；④ 向量检索历史（RAG over history）；⑤ **工具结果截断**（observation truncation）；⑥ 结构化状态/checkpoint（提炼任务状态）；⑦ 换出/分页（MemGPT spill/load）。
- **项目落地**：**窗口 20 条 + 水位线增量摘要 + 双层截断**（工具结果回注 2000 / 工具内 4000 字符）；③④⑥ 按"无触发不引入"暂缓（详见 [08-记忆质量改进](../roadmap/current-release/08-记忆质量改进.md) 与长程任务思考）。
